# 材策环境部署（Harness dev11）

安装环境是插件功能的一部分。首次使用无需先安装 Python、uv、材策核心或 MatterGen；已有环境仍可用手动连接。Harness 本身及模型账户由用户安装和配置。

## 从下载到第一次任务

1. 从本仓库 `releases/harness/0.2.0-dev.11/` 目录下载 `MatPilot-setup-0.2.0-dev.11.zip`，解压并核对 SHA256SUMS.txt。GitHub 文件页面点击 Download raw file 即可下载。
2. 在 DeepSeek Harness `0.2.1-rc.2` 的“插件 → 添加插件”中选择 `dsh-matpilot-0.2.0-dev.11.tgz` 的绝对路径，安装并启用“材策 MatPilot”。
3. 打开材策插件页，点击“复制环境检查指令”，在对话中发送：

   > 检查材策运行 MatterGen 的环境，并准备安装计划。保留现有环境，先不生成材料。

4. 检查结果会说明 GPU、WSL、架构、空间、目录和下载来源。查看计划后发送“按刚才的计划安装材策环境”。安装在后台继续，可询问“材策安装到哪一步了”。用户已明确授权安装时无需重复确认同一计划。
5. 失败时发送“查看材策安装失败原因，恢复这个安装任务”。恢复复用原计划和已校验的下载；仍在运行的任务不能被再次启动。版本配方改变后须重新生成计划。
6. 安装结束分别报告 Python/依赖、CUDA/权重、MCP 连接。此时真实材料计算仍关闭。若要验证生成，发送“用一个候选验证刚装好的 MatterGen，允许这一次 GPU 计算”。
7. 一个候选验证通过后，发送“连接这个环境并启用真实计算”。随后可准备正式材料任务，提交仍需要对应任务计划授权。

示例提示词只是容易发现的入口；执行使用固定工具和安装配方，不由大模型临时拼装任意安装脚本。用户也可以使用同义表述。插件设置页的复制按钮只复制文本，不假装已经执行了检查。

## 支持与安装范围

- 支持 Linux x86_64（glibc >= 2.28）及 Windows 的 WSL2 Linux x86_64；默认发行版 Ubuntu，可指定已安装的其他 WSL2 发行版。
- 真实生成需要该 Linux 环境能访问 NVIDIA GPU；仅有 `nvidia-smi` 不能证明兼容，安装后还要测试 PyTorch CUDA 分配，最后以真实小任务验证。
- 系统需有 curl、tar、sha256sum、timeout。缺少 WSL、驱动或系统工具时给出阻塞原因和后续操作。本版不自动修改 BIOS、安装驱动、执行管理员系统安装或替用户完成重启；完成后重新检查即可。
- 新安装要求至少 12 GiB 可用空间，已有托管环境/恢复/复核要求至少 2 GiB。该值是安装策略下限，实际空间随平台与缓存增加；不是容量保证。Windows 同时检查系统盘，WSL 在其他盘的复杂存储布局可能被保守拦截。
- Python、材策核心和 MatterGen 分别由受管路径隔离，保持已有 Conda/系统 Python 不变。默认目录为 Linux 用户目录下 `.local/share/matpilot/mattergen-1.0.3-cu121-v1-模式`。
- `demo` 必须明确选择，只检查固定样本流程，不安装 MatterGen 或提供真实材料成果。不能因为缺少 GPU 就自动改成 demo 并报告部署成功。
- 这是联网安装包。包含安装器、固定依赖清单、材策 wheel 和按官方固定提交构建的 MatterGen wheel；Python、CUDA Python 依赖和约 512 MB 权重按需下载。完整依赖下载为数 GB；不是离线镜像。

固定版本、URL、SHA256、模型提交均见插件内 `deployment/recipe.json`。安装使用 hash 锁定依赖并校验引导程序、Python、wheel 和权重。权重保持上游许可证。本版不安装 DiffCSP++。

## 网络、失败与恢复

Windows 下载沿用现有 HTTP(S) 代理配置。WSL NAT 无法使用 Windows localhost 代理时，安装任务创建短时、鉴权、来源受限且仅允许官方依赖域名的连接转发；TLS 仍在客户端与源站间校验，任务结束后关闭。不会修改防火墙或全局代理。复杂 PAC/SOCKS/企业代理需要用户先配置可用网络，不保证自动解决。

状态默认保存在宿主用户目录 `.matpilot/deployment`，包含 `plans/`、`jobs/`、`events/`、`logs/`、下载缓存和 `active.json`。开发/独立 CLI 可用 `MATPILOT_DEPLOYMENT_STATE` 指定另一状态目录。日志脱敏后才能对外分享。

下载中断保留 `.partial`，续传失败时重新下载该文件；校验失败的文件保留为 `.rejected-*` 并报错。恢复会重新校验和执行幂等步骤，成功安装的依赖由 uv 复用。安装进程退出时任务标为 interrupted，不由模型猜测成功；Windows 应用退出后后台进程是否存活取决于宿主，重新打开后查询状态。

安装/验证全局互斥，避免同一状态目录同时改环境。真实验证的恢复保留同一材料任务幂等键，不额外增加样本预算；失败的真实材料任务不会因“恢复安装”悄悄再采样。要再试一个样本必须明确新建验证任务。

## 原流程和新流程的对照

| 环节 | 原 dev10 + 官方手动流程 | 新部署工具 |
|---|---|---|
| 起点 | 用户自行准备 Python/模型环境 | 无 Python 时仍能调用部署检查 |
| 选择版本 | 查文档并处理依赖兼容 | 固定官方提交、依赖锁与文件校验 |
| 安装 | 多个终端命令、人工传路径 | 同一计划安装隔离核心、模型、权重 |
| 网络/失败 | 阅读报错后人工定位重试 | 明确失败阶段，保留状态与下载后恢复 |
| 连接 | 填 Python/config 路径 | 验证通过后自动生成并连接配置 |
| 验收 | 分散执行命令，容易把安装等同于可用 | 导入、CUDA、MCP、真实样本分层报告 |
| 结果留痕 | 操作者自行记录 | 计划、事件、时间、错误、验证结果持久化 |

原文件未被新说明覆盖：见 `benchmarks/deployment/baseline/` 的 dev10 快照、固定官方 README 与身份校验。正式评估分 A 人工官方流程、B 通用 Harness 辅助、C 材策部署工具；同硬件、同网络、同依赖、冷/热缓存分开，保留失败。完整协议见 `benchmarks/deployment/protocol.md`。

这些是工程行为差异；它们支持测量是否降低门槛，不能直接变成人工提速百分比、用户成功率或科研首创结论。此次开发联调与未来独立用户实验必须分别报告。
